# Android release preparation

## Current build path

Use the manual [local Linux builder](ANDROID_LOCAL.md) for Android. Codemagic
is reserved for iOS; the old Android workflow has been removed from the active
configuration. The sections below document the original Android setup and its
verified 0.1.0 (13) baseline. They are historical unless explicitly marked current.


## Design and implementation plan

Goal: manually build a signed Google Play AAB and installable release APK in
Codemagic, using the existing Expo 57 dependencies. Publishing remains a separate
action after review.

The Android project is generated by Expo prebuild in CI. A local config plugin
replaces the template's debug release signer with an environment-only upload
signer. A tested Node helper validates required settings, allocates a positive
version code, and writes the keystore into a private temporary directory. The
build script removes that directory on exit and exports only checked binaries
and validation reports. iOS configuration and its APNs integration stay intact.

1. Write failing tests for missing/invalid credentials, version bounds, private
   keystore creation, and replacing the actual installed Expo Gradle template.
2. Implement the helper and Android config plugin; block unused permissions and
   turn off Firebase messaging auto-initialization on Android.
3. Add a manual Codemagic workflow with Node 22.22.2, Java 17, generated Gradle
   wrapper, lint/typecheck/tests, native generation and signing validation.
4. Validate generated manifest and Gradle configuration locally. Cloud builds
   must verify the APK/AAB signer, target SDK and native library 16 KB alignment.
5. Document encrypted variables, versioning and first Play upload requirements.

No dependency changes, generated Android files, private keys, automatic store
publishing, or generated iOS changes are part of this work.

## Codemagic configuration

Start `pf-android-release` manually from a reviewed branch. This workflow has no
push trigger or publishing section. It uses the existing `mac_mini_m2` builder with the Xcode 26.6 image, already
available to this PF Codemagic account. The initially selected `linux_x2` builder
was rejected by the account billing plan before compilation, so no Linux upgrade
is required. Its toolchain is Node 22.22.2, Java 17, Android platform/build tools
36, NDK 27.1.12297006 and CMake 3.22.1. It uses
the generated Gradle wrapper (currently 9.3.1), not the system Gradle. SDK tools
and Maven/npm downloads need network access. The build invokes SDK Manager at
`$ANDROID_SDK_ROOT/cmdline-tools/latest/bin/sdkmanager`, because it is not on the
Mac image's default command path. See the
[Codemagic Android guide](https://docs.codemagic.io/yaml-quick-start/building-a-native-android-app/)
and [machine configuration](https://docs.codemagic.io/specs-macos/xcode-26-6/).

After JavaScript validation, CI runs two separate actions. `prepare` installs
the SDK components, runs Expo prebuild and `:app:processReleaseMainManifest`,
then validates the merged release XML before native compilation. `build`
rechecks that manifest and compiles/signs the AAB and APK before final binary
validation. Each action recreates the same upload key in its own temporary
directory and deletes it on exit; no signing files or passwords cross steps
through artifacts. Both actions derive the same version from the build counter.

The preflight accepts exactly one `AndroidManifest.xml` under
`android/app/build/intermediates/merged_manifest/release/processReleaseMainManifest`
(or the corresponding `merged_manifests` directory). Missing or ambiguous
outputs fail rather than selecting a debug or unrelated manifest. The Expo XML
parser checks package, version code, target SDK, debug status, and the same
permission allowlist used for the final APK. The merged manifest is saved as
`merged-manifest-report.xml`, including when permission validation fails, so
unexpected transitive permissions can be diagnosed without another full build.

Create the encrypted environment group `pf_android_signing` and grant this
Codemagic application access. Never put these values in source control:

| Variable | Meaning |
| --- | --- |
| `PF_ANDROID_KEYSTORE_BASE64` | Base64 of the production upload keystore; retain a secure offline backup. |
| `PF_ANDROID_STORE_PASSWORD` | Password that opens that keystore. |
| `PF_ANDROID_KEY_PASSWORD` | Password for its private key. PKCS12 should use the same password as the store. |
| `PF_ANDROID_KEY_ALIAS` | Alias of the upload key, never `androiddebugkey`. |
| `PF_ANDROID_STORE_TYPE` | Optional `PKCS12` (default) or `JKS`; must match the file. |
| `PF_ANDROID_VERSION_CODE` | Optional explicit positive integer, at most 2100000000. |

PKCS12 created with OpenSSL is supported directly by Java/Gradle. The keystore
must contain the alias, private key and signing certificate. The build verifies
the alias with `keytool`, rejects Android Debug certificates, and compares both
final binary certificate fingerprints with the supplied certificate. No
password is placed in a command argument. Keystore bytes are written with mode
0600 into a private temporary directory and removed on exit; they are never
included in artifact patterns. Keep the key for future updates, even when
Google Play App Signing manages the distribution key.

Without an explicit version, the build uses `PROJECT_BUILD_NUMBER + 1`.
Codemagic defines this as its app-wide build counter, unlike the per-workflow
`BUILD_NUMBER`. Each new build attempt therefore receives a positive distinct
code within this Codemagic application. Upload codes must be greater than every
previously uploaded code; download/upload builds in increasing order. If an app
was uploaded elsewhere, a Codemagic project was recreated, or an override raised
the code above the counter, set an explicit higher code for subsequent builds.
Missing, empty and invalid counters fail the build. See
[Codemagic counters](https://docs.codemagic.io/yaml-basic-configuration/environment-variables/).

CI collects outputs from the explicit `/tmp/pf-android-artifacts` directory
(`PF_ANDROID_ARTIFACTS_DIR`), avoiding monorepo working-directory ambiguity.
Outputs are `PuntosFieles-<versionCode>.aab`, `PuntosFieles-<versionCode>.apk`, a
JUnit test report and validation reports. The AAB is for Google Play. The APK
can be installed directly for device testing; after Play App Signing uses its
distribution certificate, a sideloaded upload-key APK and Play installation may
need to be uninstalled before switching between them.

## Native validation and platform behavior

Expo 57 uses React Native 0.86, with Node 22.13 or newer required. This app pins
Expo 57.0.32 and RN 0.86.3. See the
[versioned Expo documentation](https://docs.expo.dev/versions/v57.0.0/).

Local `expo prebuild --platform android --no-install --clean` and
`node scripts/check-android-project.mjs` verified:

- `applicationId` is `com.puntosfieles.customer` and release binds to
  `signingConfigs.pfRelease`. Missing signing settings stop release tasks;
  there is no debug signer fallback. Local debug tasks retain Expo's debug key.
- `android/app/build.gradle` reads `rootProject.ext.targetSdkVersion`; Expo's
  version catalog loads RN's `gradle/libs.versions.toml`, currently target/compile
  API 36, build tools 36.0.0 and AGP 8.12.0. CI also inspects the compiled APK's
  target rather than trusting source configuration.
- `android:allowBackup="false"`, SecureStore backup exclusion resources, and
  `android:enableOnBackInvokedCallback="true"` are retained. Release has no
  cleartext traffic override.
- `newArchEnabled=true`, `hermesEnabled=true`, and
  `expo.useLegacyPackaging=false` remain enabled. RN's Gradle plugin and
  RN/Hermes, Expo Modules Core, Reanimated and Worklets builds set
  `ANDROID_SUPPORT_FLEXIBLE_PAGE_SIZES=ON` for the selected NDK.
- The source manifest explicitly removes storage, overlay, microphone,
  notifications, boot, vibration, wakelock, biometric/fingerprint, FCM receive,
  install-referrer and OEM launcher badge permissions. The merged manifest and
  compiled APK must contain only Internet, NetInfo's
  network/Wi-Fi state, and AndroidX's app-scoped non-exported-receiver permission; anything
  else fails for review.
- `firebase_messaging_auto_init_enabled=false` and
  `firebase_analytics_collection_enabled=false` are Android manifest metadata.
  `expo-notifications` remains linked for iOS APNs; Android push is unsupported
  by the existing application UI/platform logic. Neither Firebase credentials
  nor `google-services.json` is needed for this build.

Permission audit: the installed packages' main/release source manifests request
Internet, network/Wi-Fi state, notifications, boot completion, and external
storage. The unused permissions are blocked. Expo Application also depends on
`com.android.installreferrer:installreferrer:2.2`, whose published AAR requests
`com.google.android.finsky.permission.BIND_GET_INSTALL_REFERRER_SERVICE`. Its
native connection starts only when `getInstallReferrerAsync` is called; PF and
the other installed JavaScript modules do not call this optional API. Removing
that unused permission preserves application identity/version APIs. The early
merged-manifest check covers Maven/AAR permissions that source-only scans cannot
fully enumerate. See [Expo Application](https://docs.expo.dev/versions/v57.0.0/sdk/application/)
and [Android manifest merging](https://developer.android.com/build/manage-manifests).

The actual merged manifest from build `6af2e432546991aef033c9a1` also exposed
16 OEM launcher badge permissions from Expo Notifications' ShortcutBadger
dependency. PF never calls the badge-count APIs and its native push support is
iOS-only, so all 16 are blocked. The permission-only fixture in
`tests/fixtures/android-merged-permissions-20261110.xml` preserves that build's
20 requested permissions and provenance. Regression tests confirm that applying
the configured blocks leaves exactly the four approved permissions and that
every badge permission remains rejected by the final APK validator.

Google Play requires new apps and updates to target API 36 or newer from
August 31, 2026. See the [current Android target policy](https://developer.android.com/google/play/requirements/target-sdk?hl=en).

CI checks APK ZIP alignment with `zipalign -P 16` and all arm64/x86_64 ELF LOAD
segment alignments in both APK and AAB. It also rejects an unaligned GNU_RELRO
end when the same containing writable LOAD segment continues past it, including
zero-filled BSS memory. Aligned RELRO ends, exact LOAD ends, and libraries with
no RELRO segment satisfy this specific compatibility check.

The AAB must explicitly request `PAGE_ALIGNMENT_16K` with uncompressed native
libraries enabled in `bundletool dump config` JSON. Missing, malformed or other
alignment values fail validation. CI downloads Google's
[bundletool 1.18.3 release](https://github.com/google/bundletool/releases/tag/1.18.3)
and verifies SHA-256
`a099cfa1543f55593bc2ed16a70a7c67fe54b1747bb7301f37fdfd6d91028e29`
before running the jar; the temporary jar is cleaned up with the signing folder.
This adds no app dependency. The raw bundle configuration is retained as a
validation report.

These checks detect packaging and native library problems but do not replace
launching the app on a 16 KB emulator or device. The resulting AAB must also pass
Play Console's bundle checks before distribution. See
[Android's 16 KB guidance](https://developer.android.com/guide/practices/page-sizes).

The local environment has no JDK or Android SDK. Native compilation and signing
have succeeded in Codemagic, but the first binaries were withheld because the
final permission check found the now-blocked install-referrer permission. A
subsequent cloud build must pass all manifest and binary checks before artifacts
are released; device runtime remains unverified. After downloading the APK, test login/logout, QR/card display, reward
redemption, refresh/offline states, text scaling, back navigation and a cold
launch on an Android device; Android notifications should remain unavailable.

## Google Play upload and release

PF's app record and publisher access are configured. The initialized Play record
accepted version **13** through the Android Publisher API; its first validated
AAB is saved as an **internal-testing draft**. It has not been rolled out to
testers or published to production. See the verified checkpoint below.

For later releases, build a new validated AAB with a version code greater than
all previously uploaded versions. Use the existing PF publisher credentials for
an explicitly requested upload. Keep release edits limited to the intended
track and check existing drafts before replacing them. This Codemagic workflow
produces artifacts only; it does not automatically upload or roll out a release.

Before distributing through Play, complete the required app setup and testing
configuration: store listing, privacy policy, Data safety, app access, content
rating, target audience, testers, and any account-specific review requirements.
Real customer authentication still needs the configured verification-code
channel to be online. Production publication is a separate reviewed action.

References: [Codemagic Play publishing](https://docs.codemagic.io/yaml-publishing/google-play/)
and [Google Play API setup](https://developers.google.com/android-publisher/getting_started).
