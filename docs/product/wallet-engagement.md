# Wallet engagement — website/server implementation, 2026-11-11

Passes now include a points-based reward choice or next target, using available points only. Pending points remain a separate balance. The authoritative snapshot uses one PostgreSQL statement to read the pass, current balance, original protected reward/earning terms, branch scope, stock, availability and redemption guards. The smallest eligible points cost is shown; a choice already covered by the available balance takes precedence over a future target. It is a choice, not a reserved or issued hospitality benefit. Unavailable alternatives are not substituted without customer acceptance.

Original protected names, prices, expiry and branch IDs override changed catalog terms. Protected earning rates, currency and rounding remain visible. Stock, temporary availability, current daily redemption limits and cooldowns still apply. When no reward currently qualifies, the pass links to the account instead of inventing progress.

`2026-11-11-wallet-engagement.sql` adds disabled-by-default branch location settings and a durable pass refresh deadline. Reward, availability, branch, cycle and redemption mutations invalidate pass revisions. The worker also handles expiry and cooldown/day-boundary refreshes without a points change, retaining its existing leases, retries and provider locks. Revoked passes have no progress, protected terms or locations. Identifiers, membership credentials and revocation behavior remain unchanged.

Owners configure existing branches at `GET /api/admin/branches/wallet-locations` and `PUT /api/admin/branches/:id/wallet-location`. These routes require a current owner and tenant context; mutations require CSRF. Validation accepts only an explicit boolean plus a finite latitude/longitude pair or two nulls while disabled. The service rechecks the active owner and locks the business to enforce at most ten enabled locations across concurrent requests. This does not require the multi-branch entitlement to configure an existing principal branch. Public coordinates appear in an audit event; no customer coordinates are collected or inferred.

`WalletLocations.jsx` is a default export with optional `onDirty(boolean)`. It belongs under the existing region settings; its caller must combine its dirty flag with the region form. `demoWalletLocations(url, options)` handles the two location routes in the shared demonstration dispatcher. The legacy branches page links to `/negocio/#region`.

## Provider behavior and limits

Apple receives signed pass fields and up to ten `locations`, including a neutral location relevance label. Apple documents that location relevance needs physical-device testing and that Simulator does not show passes on the lock screen. [Apple relevance documentation](https://developer.apple.com/documentation/walletpasses/showing-a-pass-on-the-lock-screen)

Existing APNs messages remain empty refresh signals. Apple updates preserve the serial and authentication token; sending a refresh signal does not establish that a visible alert was displayed. This implementation does not set `changeMessage`. That field is a format string for a changed field, not a general promotional broadcast channel. [Apple update protocol](https://developer.apple.com/documentation/walletpasses/adding-a-web-service-to-update-passes), [Apple field schema](https://developer.apple.com/documentation/walletpasses/passfieldcontent)

Google receives progress/terms text modules, an account link, and `merchantLocations` on the individual object so one customer's protected branch scope cannot affect the shared class. Empty arrays explicitly clear location and progress fields on revocation. The deprecated `locations` field is not used. [Google LoyaltyObject reference](https://developers.google.com/wallet/reference/rest/v1/loyaltyobject)

No visible field-update or promotional notification is requested: there is no `notifyPreference`, message append, or timed broadcast. Google's documentation limits notification-triggering messages and updates to three per pass in 24 hours. Nearby notifications require user notifications and precise always-on location permission; Google controls distance, dwell time and notification text. Those device/platform settings remain outside PF's control. Any future issuer-requested alerts require durable deduplication, quotas, user settings and uncertain-delivery handling first. [Google notification documentation](https://developers.google.com/wallet/retail/loyalty-cards/use-cases/trigger-push-notifications)

## Verification and remaining acceptance

Local tests use disposable PostgreSQL `activation_wallet_test` only, fixture signing certificates, intercepted Google HTTP, and intercepted browser API requests. They do not contact real Wallet providers or send customer notifications. The isolated browser build writes only to `/tmp/pf-wallet-locations-browser`; native projects, release versions, binaries and cloud build workflows are untouched.

Verified unit contracts include signed Apple ZIP manifests and detached signatures, Google identity/link privacy, available/pending separation, protected terms, guard/expiry selection, location bounds, revocation and owner/CSRF validation. PostgreSQL coverage includes RLS, invalidation with unchanged points, scheduled expiry/retry, concurrent ten-location enforcement, existing issuance and provider-write locking. Desktop/mobile light/dark browser checks cover coordinate validation, error recovery, save/removal, overflow and WCAG axe checks.

Physical-device acceptance remains outstanding: install a production-signed Apple pass and an approved Google pass, confirm the rendered front/back, account navigation, available/pending updates, reward expiry, revocation and branch relevance with each platform's user settings enabled and disabled. Record observed timing and display behavior; do not infer device behavior from the browser or fixture package tests.
